# Rewriting rlsbl in Go: decisions and deviations

Append-only companion to `todo/go-rewrite-plan.md`. Each entry records an implementation decision made along the way, or a deviation between the plan and what the work found, at the moment it is made: what the plan says, what the work showed, and what was built instead. Entries marked "awaiting a ruling" are built as described and stay open until a ruling is appended.

## Folding the orchestrator rulings into the plan

- The standard library's `go/parser` stays in rlsbl, used only for the import sites of `rewrite go-module-path`, the ldflags symbol checks, and the guard tests; rlsbl has no tree-sitter or other parser dependency and analyzes no source for checks.
- Because confidentiality is derived from license periods, `transition declassify` takes a repeatable `--license <releasable>=<SPDX>` and closes the proprietary periods itself, and `transition license` refuses a change that would leave a repository with no proprietary releasable while it is declared private. Awaiting a ruling.
- Release tags inside a squashed proprietary period are moved to the squash commit, and their release archives become `unrecoverable`, since the released tree no longer exists. Awaiting a ruling.
- safegit has no squash rewrite, so the safegit slice adds a squash mode to `safegit scrub`.
- The migration writes a `[python_tools.lint]` table for each pypi member unless its `rlsbl:ruff-lint` option entry is `off`, so `ruff-lint` enforcement continues as strictcode's lint rule.
- selfdoc scans every repository, including ones without a lifecycle-and-license record, and its `repository-visibility` check refuses a private repository with no proprietary releasable. Awaiting a ruling.
- The cgofree tree-sitter modules become `github.com/stricttools/cgofree/generated/<dir>`, tagged `generated/<dir>/vX.Y.Z` starting at `v0.1.0`, and the `/generated/` ignore rule is narrowed so those directories are tracked.
- The minimal-record command for repositories rlsbl does not manage is `rlsbl transition init-minimal-record`.
- Open before any cgofree release (awaiting a ruling): cgofree has no git remote, so the plan makes a public `origin` at `github.com/stricttools/cgofree` a precondition; and cgofree's own `docs/decisions.md` records an owner ruling that tree-sitter ships as one repository per module, which the subdirectory-module ruling contradicts.
- Open before saferm's release (awaiting a ruling): saferm's npm per-platform package names follow `<package>-<os>-<cpu>` without win32, by analogy with rlsbl's approved names.

## Fixes after the blind review of the plan

- The `strictcode` check no longer compares versions. A strictcode built from source reports the version its `VERSION` file held before its release bumped it, so a version floor would refuse every release in the release order, strictcode's own included. The check asks `strictcode registry rules --json` (a read-only command the strictcode port adds, since strictcode has none) for the rules strictcode implements, and refuses, naming each missing rule, when a rule rlsbl requires is absent.
- "rlsbl-owned files" in the migration's commit means the exact list of paths the migration itself wrote or removed, the lifecycle-and-license record, `strictcode.toml`, and options entries included. The migration commits that list and never any other path, so other sessions' uncommitted work is untouched, and a path it would write that already has uncommitted changes refuses the run, naming it. The earlier wording ("only rlsbl-owned paths") contradicted the migration writing files rlsbl does not own.
- Only mutating commands write the confidential-name index; read-only commands only read it, so a read-only command never changes state. The lifecycle library performs no file write of its own: it takes an injected `lifecycle.FileWriter`, which rlsbl backs with its strictcli effects handle (so `--dry-run` records those writes) and selfdoc and safegit back with their own.
- The changelog entry schema, format version 2, keeps the optional `packages` field with its Python meaning (the member packages an entry affects, printed as a bracketed prefix), because dropping it would lose data the Python writes and prints.
- `id` is required in format version 2. Its format is the Python's `<timestamp_hex><uuid4_hex>` (48 hex characters), not a ULID as the plan said. The migration mints an id once for each historical entry that lacks one, and the minted ids are committed with the migration; minting is not required to be deterministic, because it happens once.
- A `retired` lifecycle period may name a subject the declarations no longer hold, because a closed release history's subject is usually gone from the declarations. A closed history's changelog, archives, version file, and config move to `.strictmetadata/retired-release-histories/<subject>/`, a per-subject directory beside the per-type directories of active releasables, so the record of what it released has a home that nothing releases from and `releasable-residue` does not report.
- Pending identity changes are representable: a pending `[[identities]]` entry carries `effective_version` in place of `from`, and the release of that version converts it at its archive step into a period starting on the release date (its release commit's committer date), closing the identity it replaces. The record's facets add `project-name` and `tag-format`, so every facet of the Python's `identity-transition` events has a home.
- The migration reads each repository's GitHub visibility (`gh`, read-only) and refuses a private repository with no proprietary releasable, naming it, until the operator declares its releasables' licenses through `--licenses`. Confidentiality is derived only from proprietary license periods and private repositories without a proprietary releasable are not designed for, so the migration refuses them rather than inventing a classification.
- Go registry reads may fetch `@v/<version>.mod`, but only for a version `@v/list` has already returned; `@latest` is never requested. `go-deprecation-published` needs a published version's `go.mod` to read the deprecation comment, and a version the listing returned is published, so the read cannot burn a version. The check, with `old-repo-archived`, reads the closed identities from the record's `[[identities]]`.
- strictcode's lint, format, and type-check adoption are strictcode options (`strictcode:lint`, `strictcode:format`, `strictcode:type-check`: `error > warn > off`, default `off`, path scope), and every strictcode rule is an option `strictcode:<rule id>` defaulting to its severity. The `[python_tools.<rule>]` tables stay as declarations of which command runs over which paths, and the per-rule and per-group `enabled` and `severity` switches of `strictcode.toml` are deleted. This follows `~/Projects/CONTEXT/strict.md` (options are the only sanctioned switch) and the ruling that every release runs strictcode with all its rules; `rlsbl:strictcode` stays `error`. It supersedes the earlier entry in this file that made the presence of a `[python_tools.lint]` table the choice: `rlsbl:lint`, `rlsbl:format`, and `rlsbl:type-check` entries become the matching strictcode entries, and `ruff-lint` becomes a `[python_tools.lint]` declaration plus a `strictcode:lint` entry for each member it covered, unless the repository's `rlsbl:ruff-lint` entry (scope `none`) is `off`.
- A config naming a removed target, or carrying a key the audit refuses, is refused by the migration, which names the hand edit; the coordinator performs those hand edits at migration time. The Python is deleted only after the migration is committed in every rlsbl repository, and `migrate records` stays in the Go tree until then and is deleted in a commit of its own, separate from the switchover commit.
- The migration derives a standalone releasable's name the way the Python does (`create_standalone_releasable` in `rlsbl/workspace.py`), records it in `releasables.toml`, and the Go rlsbl reads only the recorded name. Whether a repository is a workspace is read from a required `repository_layout` field (`standalone` or `workspace`), which the migration sets from the presence of `.rlsbl-monorepo/workspace.toml`, not from the member count, because a workspace whose only member is the root member is still a workspace.
- browserbuddy's quiet deprecate-and-yank runs before its classification, and after classification every registry write for it is refused (`release yank` refuses its registry steps for a proprietary releasable), because a classified releasable publishes nothing anywhere public. A `deploy_command` is refused on a releasable that is not proprietary, because servers are proprietary.

## Decisions made while starting the build

- The strictspec certificate rule in strictcode is an opt-in strictcode option, `strictcode:strictspec-certificate`, defaulting to off like the other adoption options; the `[strictspec_certificate]` table in `strictcode.toml` holds only declarations (the paths it checks), and its presence switches nothing. This follows the options rule in strict.md, which forbids a table's presence acting as a switch.
- No per-slice auditor runs during the build; the blind audit of the finished Go against the plan, the decisions file, and this file covers every slice, because no slice's code can be compiled before the first-run phase anyway.

## The cgofree tree-sitter modules

- The recipe module-path rule requires a recipe of `recipes/` to give each repository the module `github.com/stricttools/cgofree/generated/<repository name>`, the directory it is generated into, because a subdirectory module's path must match its location; the old rule accepted any `github.com/cgofree/<name>`. A recipe given by path is refused a module under `github.com/stricttools/cgofree/generated/`, replacing the old refusal of `github.com/cgofree/`. The red test was committed before the rule change, as its own commit.
- The rule covers every recipe of `recipes/`, so the QuickJS-ng recipe follows too: its module becomes `github.com/stricttools/cgofree/generated/quickjs-ng`, with its recipe Go files' imports and their `module.files` SHA-256 pins, its `go.mod` stub, and its `record.toml` `import_path`. `generated/quickjs-ng` stays ignored and is not rewritten; it is stale until the next `cgofree generate --library quickjs-ng`.
- The tracked tree-sitter directories were rewritten by text substitution of `github.com/cgofree/tree-sitter` with `github.com/stricttools/cgofree/generated/tree-sitter` (go.mod files, imports, and the grammar package comments), not regenerated. Import order is unchanged, so gofmt's sorting still holds. They are 103 files, about 10.4 MB, the largest a 1.4 MB embedded `module.dat`.
- `record.toml` takes the new `import_path` values only; its `recipe_sha256` and the packages' `sha256` and `go_bytes` still describe the recipes and generated files before the path change, so `cgofree verify` and `CheckGenerated` report both libraries as changed since the last generate until the coordinator runs `cgofree generate` and `cgofree verify` for each in the first-run phase. Those runs rewrite the record and must leave the tracked tree-sitter files byte-identical to the committed ones.
- `internal/recipe/cgofree_recipe_gen.go` is strictspec output (mode 444); its schema description was edited by hand to match the edited `.strictspec/recipe.schema.toml` and the mode restored. The first-run phase reruns `strictspec gen --manifest strictspec.toml` in cgofree to confirm no difference.
- The pipeline's `GOPRIVATE` drops `github.com/cgofree/*`: `github.com/stricttools/cgofree`, already listed, covers every generated module.
- Synthetic `github.com/cgofree/tree-sitter...` paths in cgofree's recipe, pipeline, record, and release-changes tests move to the new paths, so the tests describe the modules as they are now.
- Awaiting a ruling: `cgofree release` (`internal/release`, `internal/cli/release.go`, and `internal/cli/release_test.go`) publishes each generated repository to its own repository of the cgofree organization and refuses any recipe whose module is not `github.com/cgofree/<name>`; after the rule change it refuses every recipe, and its tests fail. The plan releases these modules through rlsbl declarations instead and says nothing of the command. Whether it is deleted or reworked to release subdirectory modules is a user-visible decision, so it is untouched and `github.com/cgofree/tree-sitter` paths remain in it and its tests.
- cgofree's `docs/decisions.md` records, as a revision citing rlsbl's `todo/go-rewrite-decisions.md`, that this ruling supersedes its one-repository-per-module ruling for the tree-sitter modules, tagged `[run]` because the ruling is the campaign leader's, not the owner's.
- strictcode's local, gitignored `go.work` keeps its `use` directories (they did not move) and its `replace` lines now name the new module paths; it is not committed.

## The lifecycle-and-license library

- The library never reads the clock: every question about what is in effect takes the date. `PublishAllowed(subject, output, visibility, on)` and `ConfidentialNames(on, repositoryName)` gain a date beside the plan's parameters, so the release, the checks, and the tests decide the date.
- `ConfidentialNames` also takes the repository's name, because the record does not hold it and the `confidential-names` rule includes it when no releasable carries a non-proprietary license; it refuses when the name is needed and empty. Its names are the proprietary subjects, their identity values other than `tag-format` values (which are patterns, not names), the registry names recorded for them, the codenames, and the distinctive terms, deduplicated ignoring case.
- Each rule has one exported evaluation method on `*Record`: `VisibilityAllowed`, `PublicOutputAllowed`, `PrivateRepositoryOutputAllowed`, `ReleaseAllowed`, `ConfidentialNames`, `ProprietaryPeriods`, `TagOwner`, `CheckRegistryNamesHeld`, and `CheckClosedPeriodsFinal`; `PublishAllowed` runs both publishing rules and `CheckAppendOnly` both permanent rules.
- `Visibility` has a third value, `VisibilityUnknown`, ported from the Python guard, which never read an unanswered visibility question as public: it refuses the outputs that record the repository's identity and fails `VisibilityAllowed`. As in the Python guard, a repository GitHub reports private has those outputs refused even when its record is public; `VisibilityAllowed` refuses that state on its own, for `repository-visibility`.
- `proprietary-refuses-public-output` refuses every output for a proprietary subject, and `RegistryPackage` covers a publish, an npm deprecate, and a Go retract alike, so `release yank` asks it for its registry steps.
- Validation is split by what it needs. `Load` and `Parse` run the built-in schema and the checks that need neither the date nor the declarations (period bounds and overlaps, at most one open period, one of `from` and `effective_version`, at most one pending entry per subject and facet, no `until` on a pending entry, tag patterns without brackets, unique registry names, unversioned tags, codenames, and terms). `(*Record).Validate(on, declared)` adds the refusal of codenames and terms while public and the subject check. The subject check covers open and pending entries; a closed period and a registry name may name any subject.
- A period whose `until` equals its `from` is accepted as an empty period, so a release that converts a pending identity on the day the identity it replaces began can still close that one.
- Tag patterns are globs in which `*` matches any run of characters, slashes included (as git's tag listing does), and `?` matches one character.
- The index is a loaded value rather than package functions: `index.DefaultPath()`, `index.Load(path)`, and `(*Index).Upsert`, `Remove`, and `Scan`, plus `index.ScanTerms(text, terms)` and `index.NormalizeOrigin`. The path parameter keeps tests away from the machine's real config directory. The file holds `format_version = 1` and `[[repositories]]` tables with `origin` and `names`; origins are normalized to `host/owner/repo` (or `file:///path`) by `Upsert` and `Remove` themselves; an unchanged upsert and the removal of an absent origin write nothing; an upsert with no names is refused.
- `lifecycle.FileWriter` has `WriteFile(path, data)` and `MkdirAll(path)`, with modes left to the writer, so strictcli's `Effects.Write` and `Effects.Mkdir` back it directly.
- Mutators beyond the plan's list: `CloseIdentity(subject, facet, until)`, because `ClosePeriod` takes no facet and covers the lifecycle and license tables only, and `ClearConfidentialTerms()`, which `transition declassify` needs. `ActivatePendingIdentities` returns the identities it converted. Every mutator edits a copy of the go-toml-edit document and keeps it only when the result passes the schema and the structural checks, so a refused mutation changes nothing. `Write` creates the directory's `manifest.toml` (`owner = "strictspec"`) when it is missing and refuses one naming another owner.
- The record's accessors return copies (`Lifecycle()`, `Licenses()`, `Identities()`, `RegistryNames()`, `UnversionedTags()`, `Codenames()`, `DistinctiveTerms()`), and `LicenseOn` and `LifecycleOn` return the period in effect on a date, for the checks that report it.
- strictspec's Python and TypeScript runtimes are paused, so their generated copies of the built-in schemas are not regenerated for the new schema, and the Python freshness test of those copies goes stale.
- Awaiting a ruling: a tag created while identities of two different subjects own matching patterns is refused by `TagOwner`, naming both, instead of being attributed to either. Identities of one subject matching the same tag resolve to the first in record order.

## Decisions made while building the foundation packages

- strictcli's `WithTestCoverage` is retired (applying it panics, naming its replacement), so the app declares coverage through `WithSourceTreeRoot` alone. The root is derived from the compiled path of `internal/cli/app.go` (`runtime.Caller`): a `-trimpath` build, which every released binary is, records a module-relative path and has coverage off, the way an installed Python wheel did.
- The observe allowlist (entries with category and reason, the standard in the package documentation, `Prefixes`, `Allowed`) lives in `internal/previewapply`, not `internal/cli`: the observation screen consults it and sits in the lowest layer, which `internal/cli` cannot be imported from. `internal/cli` installs `previewapply.Prefixes()`, and a test asserts the app holds that list.
- Allowlist entries dropped with their subsystems: `git subtree split --prefix` and the mirror's inspection `git clone` (mirror dropped), `gh pr list` (`prs` dropped), `ruff --version` (`ruff-lint` moved to strictcode). `git merge-file -p` is replaced by `git merge-file --object-id`, and `git hash-object -w --stdin` is added, both scratch-write: the three-way merge passes its texts and result through the object database, because the effects handle drops one trailing newline from captured stdout and cannot write scratch files under `--dry-run`. The scratch-write category is narrowed to loose objects, since observation scratch directories existed only for the mirror's clone.
- Observation is read-only by construction rather than by patching: `previewapply.Reconcile` hands `Observe` a `previewapply.Observer` (an allowlist-screened `Run` and a read-declared HTTP GET, no file writes), and `internal/git` takes a `git.Runner` interface, so git reads work under either the effects handle or an observer and git writes are refused during observation.
- The checks registry file is `internal/checks/checks.toml` (holding only `app = "rlsbl"` for now), embedded by package `checks` as `checks.Registry`; `internal/cli` passes it to `WithChecksEmbed`. The plan's package table names the registry under `internal/cli` and its checks section under `internal/checks`; the file needs one home for `//go:embed`, and the checks section's is taken.
- The version is embedded from a root `VERSION` file (created at 0.131.0, the version `package.json` holds) by a root package `github.com/stricttools/rlsbl` (`version.go`), as selfdoc does, so `go install` builds carry it without link flags. `cmd/rlsbl` passes it to `cli.New`, which refuses an empty version and a missing HTTP client (`cli.NewHTTPClient`, 60-second timeout).
- `internal/semver` refuses everything but `MAJOR.MINOR.PATCH` without leading zeros, prefix, or whitespace. A pre-release version and the `prerelease` bump are refused with the reason (the Python stripped a pre-release suffix and bumped the base; those Python test cases are ported as refusals). A leading zero, which the Python's `int()` accepted, is refused.
- `internal/git` returns errors where the Python turned a failed git read into "no", "absent", or an empty list (stash list, Autogenerated trailer, remote configured, log hashes, timeouts). The one third state kept is ancestry's: a `merge-base` exit other than 0 or 1, or a "no" in a shallow repository, is `AncestryIndeterminable`.
- Under `--dry-run` past the first recorded write, a git read is truncated by strictcli's carrier rather than answered "absent" as the Python's `tag_exists_locally` and `remote_tag_commit` did, and `Commit`'s stageable filter runs in every mode (the Python skipped it while previewing).
- `Repo.Commit` commits through safegit and refuses a missing safegit (the Python fell back to git with a note); the release checkout calls `Repo.CommitDetached` explicitly (the Python chose the tool by asking whether the directory was the active checkout). `allow_failure` is not ported (no warn-and-continue), and the repository directory must always be its own working tree's root (the Python's `expected_root` check was optional). `commit_files_if_changed` and `has_staged_or_modified` are covered by `Commit` and `Status`.
- Bugs in the Python fixed with red tests: `get_commit_files` and `get_push_changed_files` read `--name-only` output without `-z`, so a path git quotes (non-ASCII, spaces, quotes) came back C-quoted; Go reads `-z`. `detect_manual_push_branches` keyed on the local ref, so `git push origin feature:main` went undetected and pushing main to another branch was flagged; Go keys on the remote ref, which also catches deleting a release branch.
- The rewrite map reader (post-rewrite stdin, map files, git-filter-repo commit-maps) refuses, with the line number, a malformed line, an abbreviated id, a mapping to the null id, and an old id mapped twice to different ids; the Python warned and skipped them. The `old new` header is accepted only as the first content line. The pre-push stdin reader refuses a line without four fields (the Python skipped it).
- `IsAutogenerated`: no trailer or `Autogenerated: false` is false, one `Autogenerated: true` is true, and any other value or more than one trailer is refused naming the commit (the Python read everything but exactly `true` as false).
- A `git merge-file` failure is an error (the Python counted it as a conflict). Conflict markers are labeled ours, base, and theirs (the Python's carried temporary file names).
- `Repo.Push` changes one ref per push under an explicit lease (`--force-with-lease=<ref>:<expected>`, empty expected meaning the ref must not exist) with full object ids and `--no-verify`. `push_if_needed`'s compare-then-push logic belongs to the release and is not ported here. A local tag's existence is read with `rev-parse` of `refs/tags/<tag>` (the Python's `git tag -l <tag>` treated the name as a pattern). `CurrentBranch` uses `symbolic-ref`; the Python's mapping of the release checkout to its branch belongs to the release.
- From `git_util.py`, the ownership attribution (`commit_owner_names`, `filter_commits_for_scope`, `affected_members`) needs workspace ownership and moves with it to `internal/workspace`, which builds on `Repo.CommitFiles`; the subtree-remote SSH host check and `extract_ssh_host` are dropped with the mirror. From `utils.py`, the timeouts and project-root discovery go to the declarations, `is_virtual_uv_root` to dependencies, changelog section extraction to changelog, the gh helpers to github, the Go module path to gomodule, the gitignore entries to scaffold, and `require_tool` becomes each caller's `exec.LookPath` refusal.
- `StatusArgs` requires the untracked mode to be stated (the Python's `None` meant git's default). Git commands that write stream their output, so what git says about a failure reaches the operator (the effects handle's failure error carries only the exit code); saferm deletions stream too, and the saferm argv puts `--` before the path.
- `internal/testsupport` builds fixtures with `os/exec` and `os` directly: it is imported only from `_test.go` files (the layering test refuses any other importer, and the harness itself imports nothing of rlsbl). Its throwaway application, which runs one handler under test, is exempt from the guard refusing command registration outside `internal/cli`. It adds a fake safegit (a shell script performing `safegit commit` with git) and `PathOnly`, which leaves only named programs on `PATH`. The fake gh answers by whole argv, in order when several answers share one argv, the last repeating; an unanswered argv exits 97.
- The layering test checks non-test files: a package under `internal/` missing from the order fails, `cmd/rlsbl` may import only `internal/cli` and the root package, and the root package imports nothing of the module. The banned-word guard checks file names, identifiers, comments, and literals of every Go file outside the scratch directories, `testdata`, and nested modules.
- `scripts/go-suite.sh` runs a gofmt check before `go vet`, as orxtra's suite does. `experiments/` and `screenshots/` carry a committed `go.mod` (and `!go.mod` in their `.gitignore`), so `go vet ./...` and `go test ./...` leave them out.

## Enforcement in selfdoc and safegit

- safegit requires `github.com/stricttools/strictspec/go v0.5.0`, the published version selfdoc already requires, and both build against the local strictspec tree through their gitignored `go.work` (safegit's gained `use ../strictspec/go`), because v0.5.0 lacks the `lifecycle` package and requiring an unpublished version in `go.mod` would let a build outside the workspace ask the module proxy for it. The require lines are raised to strictspec's next release when it is published. safegit's `go.sum` carries the v0.5.0 lines; the `go.mod` hash of strictcli v0.37.0, which strictspec v0.5.0 requires, is added by the first-run `go mod tidy`.
- safegit's commit screen runs inside the commit pipeline, through a `Screen` the commit command hands it, after the tree is written and the commit-msg hook has had the message and before the commit object exists, so a refusal writes nothing and `--dry-run` screens too. It scans the message as the hook left it, before safegit's session trailer; an amend's delta is taken against the tip it replaces, and a reword scans the message alone. Only `safegit commit` (with `--amend` and the reword form) is screened; `mv`, the conclusions, `merge`, `cherry-pick`, `revert`, and `pull` are not, as the plan names the commit command only.
- An added or changed line is a line of the new blob that no identical line of the blob it replaces accounts for, each old line accounting for one occurrence; this is not a minimal diff, so a line moved within a file is not rescanned. Blobs are scanned as text whatever their content, symlink targets included; gitlinks are skipped. A new path is a path the delta adds.
- Both tools key the index entry by the origin remote and take the repository name the `confidential-names` rule needs from the last segment of the normalized origin. A confidential repository with no origin remote is refused (safegit's commit, every mutating selfdoc command), naming `git remote add origin`, because its names could not be recorded. Awaiting a ruling.
- safegit's index upsert or removal runs before the commit is attempted, whether the commit then succeeds or not, and the record is evaluated at the local clock's date. A confidential-name refusal exits 1 (`General`): safegit's exit-code registry gives a new code only to a refusal whose recovery differs from every existing one, and this one's is the same fix-and-rerun.
- The index has no lock: two processes upserting different repositories at the same instant can lose one write, which the next mutating command in that repository restores. selfdoc writes the index atomically (temporary file and rename); safegit writes it through strictcli's `Effects.Write`, which has no atomic form.
- `safegit scrub squash --first <commit> --last <commit> --message <text> --reason <text>` is the squash mode. Both ends are inclusive and must be on HEAD's first-parent history. The squash commit carries the tree, author, and committer (dates included, so its committer date stays inside the period) of `--last` and the parents of `--first`; every later commit HEAD reaches is rewritten onto it unchanged; refs pointing at a folded commit, tags included, move to it; and the journal's start record maps every folded commit to it. The rewrite intent gains a squash class verified before any ref moves, and its field `Kind` is renamed `Class`. `--remap-shas-in` is not offered, since `transition declassify` runs its own metadata repair.
- `scrub squash` refuses a range with a merge commit inside it, naming the merge, because folding it would drop the merged-in history, which may hold commits from before the period. Awaiting a ruling.
- selfdoc enforces the rules on `deploy`, `blog post publish`, and `blog publish-docs` (a public documentation publish to the assembly). The `assembly` commands, which deploy the combined site the projects' publishes built, are not scanned. Awaiting a ruling.
- selfdoc scans what each output would publish: every file under the built output directory for `deploy` and `blog publish-docs`, and every file `blog post publish` pushes, manifests included. "No releasable may publish" is read as: the record has license periods in effect and every one is proprietary; a record with none in effect allows the output.
- selfdoc's index refresh wraps the handler of every mutating command once all commands are registered, so no command can be added without it; it reads the record at the git work tree's root, and in a directory outside any work tree it reads the project directory and writes no index entry.

## GitHub, registries, naming, and tagging

- Every gh call names its repository: `--repo owner/name` on the release, run, workflow, and secret commands, and `repos/owner/name/...` in API paths; `Client.APIGet` refuses gh's `{owner}/{repo}` placeholders. The Python's `run_gh` chose the repository through a `GH_REPO` environment variable. Callers resolve the repository once with `github.ResolveRepository(declared github_repository, origin URL)`.
- `github.Client.ReleaseExists` reads only gh's own "release not found" as absence and returns every other failure as an error. The Python's `yank`, `deprecate`, `undo`, `retry`, and `watch` read any failure of `gh release view` as "no Release", so an unanswered question decided the command; the commands that port them call this one method (test: `TestReleaseExistsReadsOnlyReleaseNotFoundAsAbsence`).
- Release notes reach gh on its standard input (`--notes-file -`); the Python wrote a temporary notes file into the working directory. `RewriteRelease` states the pre-release flag in both directions, as the Python's `edit_all_args` did.
- `github.Client.Runs` requires a limit and refuses a listing that comes back at it, the way the Release listing refuses its cap; `SearchRepositoriesByTopic` refuses when GitHub's total count exceeds the rows it returned (the search returns at most 1000), where the Python's `discover` stopped at 1000 without saying so.

Awaiting a ruling.

- `Unfinalize` (`release undo` restoring an archive as the release file) refuses when the release file holds someone's fields, naming the way out; the Python printed a warning and went on without restoring anything (test: `TestUnfinalizeRefusesAReleaseFileHoldingSomeonesWork`). The blog body archive the Python also restored is gone with blog-on-release.
- `LatestReleasedVersion` refuses an archive stating no fate, naming the backfill; the Python counted it as released (test: `TestLatestReleasedVersionReadsOnlyTheArchives`).
- Tag explanation reads every archive strictly; the Python read `shipped_as` tolerantly and passed over an archive it could not parse, which the migration's restamping makes unnecessary and which would let an unreadable archive explain nothing silently. Each moved directory gets one `release-commit-remap` event whose `releasable` is the releasable or retired subject.

## The strictcode port

- strictcode reads from `.strictmetadata/releasables/releasables.toml` only what it uses: `format_version`, `repository_layout`, and each `[[members]]` table's `name`, `path`, `releasable` (a releasable name or `false`, required), `library`, `dev_only`, `import_name`, `registry_name`, and `lint_allow`. A repository without the file is a single-project scan of one member named `_`, as before; a standalone layout's member is named as declared (`root`). `.rlsbl-monorepo/workspace.toml` is refused, naming `rlsbl migrate records`, and the old `dev_node` spelling is no longer read.
- Every refusal the plan gives a strictcode rule (an adopted option on with no declaration, an option on for a member no declared path covers, a tool that does not run or prints output the rule cannot read, ruff below its floor, an unreadable certificate) is a hard error of `strictcode analyze` (exit 2, the configuration-error status), not a finding.
- `[python_tools.<rule>]` is one table per rule, as the plan spells it: `paths` relative to `cwd`, `cwd` relative to the workspace root, both canonical. Each tool runs once over all its paths, and each problem it reports is attributed to the member owning the file and takes that member's option value (off drops it). A member is covered when a declared path lies in its territory (the member owning the path is that member). An option entry without a scope is the value of every member that has no scoped entry, so an unscoped `error` requires every member to be covered and is refused otherwise. Awaiting a ruling: one table per rule cannot give two members different `cwd`s (and so different uv environments); an array of tables (`[[python_tools.lint]]`) would, at the cost of the plan's spelling.
- The tools run through `os/exec` with a fixed 900-second timeout per invocation (rlsbl's default check timeout), not through strictcli's effects handle: strictcode does its IO directly throughout (its effects-regime migration is a strictcode todo), and `analyze` is read-only, where the handle refuses an unallowlisted subprocess. A `checks.ToolRunner` is injected, so the tests fake every tool.
- `lint` runs `uv run [--group G | --extra E] ruff check --output-format=json --quiet [--extend-exclude <nested members>] <paths>` after `uv run ruff --version` meets 0.15.20; `format` reads ruff's `Would reformat:` lines (exit 1) and `type-check` mypy's `<file>:<line>: error:` lines (exit 1). The group flags are ported from rlsbl's `resolve_tool_group_flags`; uv's legacy `dev-dependencies` gives no flag, as there.
- The option subjects follow the rlsbl options the rules come from, so migrated entries stay in their files: `dependencies` for the `deps-*` rules, `release` for `strictspec-certificate`, and `code` for the rest. `strictcode:strictspec-certificate` takes no scope (rlsbl's gate option took a path scope), because `[strictspec_certificate]` is one repository-wide declaration. Option value `warn` reports findings at strictcode's `warning` severity. Groups stay in the registry as classification and switch nothing.
- The adjudication schema is embedded in strictcode's `internal/certificate` and compiled with strictspec's runtime when first used, instead of a generated validator, so no generator run is needed for it.
- Source walks read `git ls-files --cached --others --exclude-standard` at the workspace root, and a root outside a git work tree is refused, as the Python's walk did; the test fixture helper now runs `git init`. Build-artifact and asset names (`build`, `dist`, `_build`, `static`, `public`, `assets`) are pruned only directly under a member's root, environment and cache names anywhere.
- `deps-stale` reads each Python and npm dependency member's version from its manifest of the same language; a member without a static version (a dynamic pyproject version, which the Python read from `__version__`) is not judged. Environment markers are removed before evaluation (the Python left them, so such constraints went unevaluated), and `[dependency-groups]` declarations are judged too. Go is not applicable.
- `import-cycles` leaves test modules out of the graph, as rlsbl's `circular-deps` did and strictcode did not (red lesson first).

## Publishing rules

- `internal/publishrules` reads GitHub's visibility through `github.Client.Info` (`gh api --method GET repos/<owner>/<name>`) instead of the Python's `gh repo view --json isPrivate`, and reads GitHub's `internal` visibility as private, since GitHub reports an internal repository private too. The visibility is asked only when a rule's answer turns on it (an output the private-repository-publishing rule refuses for a private repository and allows for a public one, in a repository the record does not already make confidential), and at most once per source; a question GitHub cannot answer is `lifecycle.VisibilityUnknown`, and every refusal resting on it carries the reason.
- The outputs a releasable's declarations publish (`ReleasableUses`), under any publish mode but `none`: every npm and pypi pipeline writes to a registry; a go pipeline that asks the Go module proxy (`pipelines.AsksGoProxy`: a local one, or a library) writes to a registry and notifies the proxy; a go library is a Go library; a go binary published from CI writes to no registry, since its archives go to the repository's own GitHub Releases; `homebrew_tap` is a Homebrew tap; and a published manifest names the repository when package.json has `repository`, `homepage`, or `bugs`, or pyproject.toml has `[project.urls]` or `urls` in `[project].dynamic`. npm build attestations have no declaration in Go (`provenance` is deleted), so the committed publish workflows are judged as the Python judged them: a PyPI publish step without `attestations: false`, a `--provenance` publish, and a `go list -m` against proxy.golang.org, each an output of the repository as a whole.
- Awaiting a ruling: `ScaffoldFeatures` refuses, with the reason, when GitHub's visibility cannot be had in a repository the record does not make confidential; the Python scaffolded such a repository as public and left the refusal to the release. Rendering a feature the rule could not judge, or silently leaving it out, were both rejected.
- `DeployAllowed` refuses a `deploy_command` on a releasable whose license on the date is not proprietary, and on a releasable whose publish mode is not `none`, in one refusal naming both fixes; the declarations check only the command's shape.
- The packed-artifact contents check attributes each packed file to the member owning its path in the declarations (`MemberForPath`), not through `workspace.Scope`, which leaves tool-owned paths (a `CHANGELOG.md` at any depth) unowned; a member's own `CHANGELOG.md` in its npm tarball is its own file. A file no member owns, a file another member owns (a nested member included), and a wheel entry no file of the repository matches are each refused, named with the artifact carrying it.
- Wheel entries outside `*.dist-info/` are matched by SHA-256 against the files `git ls-files --cached --others --exclude-standard` lists, so a file the build generates and git ignores matches nothing and is refused. Among identical files the one whose path ends with the entry's path is named. A dist directory holding no wheel is an error.
- A go library's Go module zip (`targets.ListUpload`) is checked too, beside the npm tarballs, wheels, and Go binaries the plan names, because the module proxy publishes it.
- Go binaries are listed with `go list -deps -json` over `install_paths` (validated as main packages), or over the module's one main package when none are declared (goreleaser's main), once per platform of `pipelines.Platforms` with `CGO_ENABLED=0`, so a file only another platform compiles is listed too. Each package inside the repository contributes its Go, cgo, C, C++, Objective-C, header, Fortran, assembly, syso, and embedded files; packages outside the repository (the module cache) are not listed.
- The confidential-name scan runs only when the record does not make the repository confidential (the plan's "in public repositories"). Of packed artifacts, every file that is valid UTF-8 and holds no NUL byte is scanned, Go source files of a binary included, though a binary carries only their compiled form.
- `internal/git` gained `Repo.FilesAt(rev, dir)` (`git ls-tree -r -z --name-only --full-tree`), which the committed workflows are read through.

## Options and the changelog

- The options registry is a value (`options.ParseRegistry`, `options.Shipped`), and every reading of entries takes one, so tests judge entries against a registry rendered from a fixture checks registry. `internal/options/gen` renders `internal/options/registry.toml` from `internal/checks/checks.toml` through `options.RenderRegistry`, which refuses a rendering strictspec refuses and a check named like a framework check or an option that is not a check. `internal/checks/checks.toml` holds no checks yet, so the committed registry holds only the framework checks, `rlsbl:test-sandbox`, and `rlsbl:ecosystem-tagging`; `rlsbl:dep-floors` and every check option appear when the checks registry is filled and the registry regenerated (coordinator step: `go run ./internal/options/gen -check`, and the freshness test `TestTheShippedRegistryIsAFreshRendering`). Until then `SettingsProblems` errors on the shipped registry, which does not declare `rlsbl:dep-floors`.
- `rlsbl:ecosystem-tagging` is filed under the `project` subject.
- `options.Load` takes the repository's declarations instead of finding a workspace itself: a path scope must name a member's path in a workspace; in a standalone repository any scope is refused (an entry without a scope covers its one project, as in Python, where a standalone project belonged to no workspace), and so is any scope in a repository with no declarations. There is no load cache: a command loads once.
- The adoption declarations: a member's `internal_dep_floors` follows `rlsbl:dep-floors` for that member, and an empty list counts as no declaration; `.strictmetadata/test-runner/test-runner.toml` follows `rlsbl:test-sandbox` for the root member, because one runner serves the whole repository. Each refusal names the declaration and the fix (deleting it, the `rlsbl options set` line that switches the option on, or the entry to delete), and the tests perform the named fixes.
- The check value resolver is per member (`Options.Resolver(memberPath)`), the function strictcli's `SetCheckValueResolver` takes; the cli builds it for the member the command runs for, after loading the options and refusing a load error, since the resolver cannot return one.
- A changelog line is read strictly: the generated validator runs on every line, and a line it refuses makes its file unreadable, every refused line named (`changelog.FileError`, with `FormatVersionOnly` for the format-version check). The Python read lines tolerantly and left schema problems to `changelog-schema`; with no legacy mode, the schema and format-version checks report the read errors and every other changelog check refuses an unreadable file.
- Not ported, awaiting a ruling: the validation cache (`.strictmetadata/.changelog-validation/<releasable>.toml`, the Python's `.validated`). In the Python only `validate_unreleased` read and wrote it, and nothing outside the tests calls `validate_unreleased` (the checks call each validation directly); the cache was also keyed on HEAD and committed, so its own commit moved HEAD past it and it could never short-circuit a validation. The path stays reserved in the layout, the tool-owned paths, and residue detection.
- With the pre-release channel gone, a `.jsonl` file in a changelog directory that is neither `unreleased.jsonl` nor `MAJOR.MINOR.PATCH.jsonl` is refused, naming it, as the release record refuses such archive names. Per-version `.md` files are not written, and a section has no "Other" group, since the schema requires a type on every user-facing entry.
- Appending reads the file and replaces it whole (the effects handle has no append), so two writers at once would lose an entry; a command that writes a changelog holds the release lock (`internal/runstate`) around its read and its write, which replaces the Python's commit-race handling in `changelog add`. Rewrites (amend, edit, remove, remap) keep every untouched line byte for byte and refuse a file changed since it was read. Go writes non-ASCII text as UTF-8 where the Python escaped it.
- `Finalize`'s warning about unreleased entries naming commits outside the range is not ported (it warned and went on); `changelog-range` and `changelog-orphans` refuse such entries before a release.
- Where `CHANGELOG.md` is written follows `repository_layout`, not the member count the plan's layout table mentions: a standalone repository writes the root file, and a workspace writes each releasable's file in its changelog directory and the roll-up at the root, as the Python did with and without `.rlsbl-monorepo/`. The roll-up is rendered from the changelog lines with the version headings at depth 3, not by stripping and stacking the releasables' files, and a releasable with no section is left out.
- A releasable's changelog scope is always `ScopeOfReleasable`, a standalone repository's included (the Python used no scope there), so a commit changing no file at all touches nothing in scope and needs no entry, in a standalone repository as in a workspace.
- `changelog add` with a batch reason on an entry within the per-entry limit is refused (a reason with nothing to exempt). A finding over the limit names removing the entry by id and adding it again with `--batch-reason`, since `changelog edit` writes no batch reason.
- The remap reads its map through `git.ParseRewriteMap`, which refuses a mapping to the null id; the Python's `load_filter_repo_commit_map`, which set pruned commits aside, is not ported here, and the history rewrites decide what a pruned commit means. Remapping covers every changelog directory on disk, retired release histories included, and `RemapGlobs` names both trees for safegit.
- The fork's upstream exclusions and URL are inputs to `changelog.NewSubject` and `changelog.PushedCommits`, because `internal/upstream` shares a layer with `internal/options`, not with the changelog, and does not exist yet. A pushed ref whose old remote commit no longer resolves is returned in `Pushed.Rewritten` for the check to report, where the Python printed a line and skipped it; a push whose commits cannot be listed is an error, where the Python skipped the check.
- The pre-push records git must not ignore are each releasable's `unreleased.jsonl` and `CHANGELOG.md`, and the roll-up in a workspace; the Python's `.validated` is gone with the cache.
- Found while porting: a released changelog file of one rlsbl repository on this machine carries a hand-written id of 32 hexadecimal digits, which format version 2 refuses; the migration must mint a new id for such a line or refuse it naming the hand edit.

## Dependencies and the rewrites

The Python's refusal of a target rlsbl does not rename that still declares `--from` is not ported: go, npm, and pypi each rename their package name. Whether the repository is a workspace is read from `repository_layout`. The rename commit is found again by its message with `git log --grep` through the effects handle, since `internal/git` has no such reader.
- `rewrite uv-path-sources` converts the member whose territory holds the working directory, reading `pyproject.toml` in its declared pypi target's directory or, without one, in the member's own; the converted names go into that member's `internal_dep_floors` in `releasables.toml`, and the `rlsbl:dep-floors` entry is scoped to it in a workspace. ## Release notes and the status commands

- A Release's notes are composed from the version's released changelog file and its archive's prose (`changelog.VersionSection`, the section `CHANGELOG.md` renders for the version, without its heading), since per-version `.md` files are gone and the Python read the section from `CHANGELOG.md`. `releasenotes.Read` refuses a version with no archive, one whose archive states no fate, one never released, and one with no released changelog file, each naming why; the Python answered no release commit and no notices for a version without an archive.
- The pre-release flag of a Release is set when the version carries a deprecate or yank notice, as those commands set it, and cleared otherwise. The Python decided it from a hyphen in the version, which no Go version carries, so its full rewrite (reconcile's update) cleared the flag deprecate and yank had set; every writer here states the flag from the record (test: `TestRewriteEditsInPlaceAndStatesTheFlag`).
- When the archive records a release commit, the marker names it even where the Release body GitHub holds names another; a body's marker is kept only for a version whose record names no commit (unrecoverable). The Python's notes re-sync kept whatever marker the body carried.
- Deciding whether a repair takes the "Latest" badge errors on every question it cannot answer (the Latest Release unreadable, a tag missing locally, an ancestry git cannot decide), where the Python logged and kept the badge where it was. The version comparison of a mirror's tags is not ported, with the mirror.

- `commit` takes files relative to the working directory or absolutely, refuses one outside the repository, and refuses a commit none of whose files changed (`git.CommitRequest.RequireChange`); the Python committed whatever safegit took.
- A fork's upstream history reaches `status` and `unreleased` as an input (`release.Fork`), which the cli reads through `upstream.URLOf` and `upstream.HistoryExclusions`.
- Added for these commands: `changelog.VersionSection`, `changelog.Subject.CoveredCommits` (which `CoverageOf` now calls), `git.Repo.Summarize` and `git.Repo.HeadBranch` (which `CurrentBranch` now calls).
- Changelog coverage: as with the earlier Go commits of this campaign, these commits carry no changelog entry.
