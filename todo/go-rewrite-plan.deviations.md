# Rewriting rlsbl in Go: decisions and deviations

Append-only companion to `todo/go-rewrite-plan.md`. Each entry records an implementation decision made along the way, or a deviation between the plan and what the work found, at the moment it is made: what the plan says, what the work showed, and what was built instead. Entries marked "awaiting a ruling" are built as described and stay open until a ruling is appended.

## Folding the orchestrator rulings into the plan

- The standard library's `go/parser` stays in rlsbl, used only for the import sites of `rewrite go-module-path`, the ldflags symbol checks, and the guard tests; rlsbl has no tree-sitter or other parser dependency and analyzes no source for checks.
- Because confidentiality is derived from license periods, `transition declassify` takes a repeatable `--license <releasable>=<SPDX>` and closes the proprietary periods itself, and `transition license` refuses a change that would leave a repository with no proprietary releasable while it is declared private. Awaiting a ruling.
- Release tags inside a squashed proprietary period are moved to the squash commit, and their release archives become `unrecoverable`, since the released tree no longer exists. Awaiting a ruling.
- safegit has no squash rewrite, so the safegit slice adds a squash mode to `safegit scrub`.
- The migration writes a `[python_tools.lint]` table for each pypi member unless its `rlsbl:ruff-lint` option entry is `off`, so `ruff-lint` enforcement continues as strictcode's lint rule.
- selfdoc scans every repository, including ones without a lifecycle-and-license record, and its `repository-visibility` check refuses a private repository with no proprietary releasable. Awaiting a ruling.
- The cgofree tree-sitter modules become `github.com/stricttools/cgofree/generated/<dir>`, tagged `generated/<dir>/vX.Y.Z` starting at `v0.1.0`, and the `/generated/` ignore rule is narrowed so those directories are tracked.
- The minimal-record command for repositories rlsbl does not manage is `rlsbl transition init-minimal-record`.
- Open before any cgofree release (awaiting a ruling): cgofree has no git remote, so the plan makes a public `origin` at `github.com/stricttools/cgofree` a precondition; and cgofree's own `docs/decisions.md` records an owner ruling that tree-sitter ships as one repository per module, which the subdirectory-module ruling contradicts.
- Open before saferm's release (awaiting a ruling): saferm's npm per-platform package names follow `<package>-<os>-<cpu>` without win32, by analogy with rlsbl's approved names.

## Fixes after the blind review of the plan

- The `strictcode` check no longer compares versions. A strictcode built from source reports the version its `VERSION` file held before its release bumped it, so a version floor would refuse every release in the release order, strictcode's own included. The check asks `strictcode registry rules --json` (a read-only command the strictcode port adds, since strictcode has none) for the rules strictcode implements, and refuses, naming each missing rule, when a rule rlsbl requires is absent.
- "rlsbl-owned files" in the migration's commit means the exact list of paths the migration itself wrote or removed, the lifecycle-and-license record, `strictcode.toml`, and options entries included. The migration commits that list and never any other path, so other sessions' uncommitted work is untouched, and a path it would write that already has uncommitted changes refuses the run, naming it. The earlier wording ("only rlsbl-owned paths") contradicted the migration writing files rlsbl does not own.
- Only mutating commands write the confidential-name index; read-only commands only read it, so a read-only command never changes state. The lifecycle library performs no file write of its own: it takes an injected `lifecycle.FileWriter`, which rlsbl backs with its strictcli effects handle (so `--dry-run` records those writes) and selfdoc and safegit back with their own.
- The changelog entry schema, format version 2, keeps the optional `packages` field with its Python meaning (the member packages an entry affects, printed as a bracketed prefix), because dropping it would lose data the Python writes and prints.
- `id` is required in format version 2. Its format is the Python's `<timestamp_hex><uuid4_hex>` (48 hex characters), not a ULID as the plan said. The migration mints an id once for each historical entry that lacks one, and the minted ids are committed with the migration; minting is not required to be deterministic, because it happens once.
- A `retired` lifecycle period may name a subject the declarations no longer hold, because a closed release history's subject is usually gone from the declarations. A closed history's changelog, archives, version file, and config move to `.strictmetadata/retired-release-histories/<subject>/`, a per-subject directory beside the per-type directories of active releasables, so the record of what it released has a home that nothing releases from and `releasable-residue` does not report.
- Pending identity changes are representable: a pending `[[identities]]` entry carries `effective_version` in place of `from`, and the release of that version converts it at its archive step into a period starting on the release date (its release commit's committer date), closing the identity it replaces. The record's facets add `project-name` and `tag-format`, so every facet of the Python's `identity-transition` events has a home.
- The migration reads each repository's GitHub visibility (`gh`, read-only) and refuses a private repository with no proprietary releasable, naming it, until the operator declares its releasables' licenses through `--licenses`. Confidentiality is derived only from proprietary license periods and private repositories without a proprietary releasable are not designed for, so the migration refuses them rather than inventing a classification.
- Go registry reads may fetch `@v/<version>.mod`, but only for a version `@v/list` has already returned; `@latest` is never requested. `go-deprecation-published` needs a published version's `go.mod` to read the deprecation comment, and a version the listing returned is published, so the read cannot burn a version. The check, with `old-repo-archived`, reads the closed identities from the record's `[[identities]]`.
- strictcode's lint, format, and type-check adoption are strictcode options (`strictcode:lint`, `strictcode:format`, `strictcode:type-check`: `error > warn > off`, default `off`, path scope), and every strictcode rule is an option `strictcode:<rule id>` defaulting to its severity. The `[python_tools.<rule>]` tables stay as declarations of which command runs over which paths, and the per-rule and per-group `enabled` and `severity` switches of `strictcode.toml` are deleted. This follows `~/Projects/CONTEXT/strict.md` (options are the only sanctioned switch) and the ruling that every release runs strictcode with all its rules; `rlsbl:strictcode` stays `error`. It supersedes the earlier entry in this file that made the presence of a `[python_tools.lint]` table the choice: `rlsbl:lint`, `rlsbl:format`, and `rlsbl:type-check` entries become the matching strictcode entries, and `ruff-lint` becomes a `[python_tools.lint]` declaration plus a `strictcode:lint` entry for each member it covered, unless the repository's `rlsbl:ruff-lint` entry (scope `none`) is `off`.
- A config naming a removed target, or carrying a key the audit refuses, is refused by the migration, which names the hand edit; the coordinator performs those hand edits at migration time. The Python is deleted only after the migration is committed in every rlsbl repository, and `migrate records` stays in the Go tree until then and is deleted in a commit of its own, separate from the switchover commit.
- The migration derives a standalone releasable's name the way the Python does (`create_standalone_releasable` in `rlsbl/workspace.py`), records it in `releasables.toml`, and the Go rlsbl reads only the recorded name. Whether a repository is a workspace is read from a required `repository_layout` field (`standalone` or `workspace`), which the migration sets from the presence of `.rlsbl-monorepo/workspace.toml`, not from the member count, because a workspace whose only member is the root member is still a workspace.
- browserbuddy's quiet deprecate-and-yank runs before its classification, and after classification every registry write for it is refused (`release yank` refuses its registry steps for a proprietary releasable), because a classified releasable publishes nothing anywhere public. A `deploy_command` is refused on a releasable that is not proprietary, because servers are proprietary.
