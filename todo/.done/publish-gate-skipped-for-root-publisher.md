# Publish gate never generated when the sole publisher is the workspace root

## Context

The publish-gating feature (gate job polling check runs for the release SHA;
publish jobs `needs` it) is generated by the inline publish-router path:
`rlsbl/commands/monorepo/publish_inline.py` + `sync.py`.

## Problem

For a single-releasable monorepo where only the ROOT package (`path = "."`)
publishes — the common "one aggregated wheel" shape — the root's `publish.yml`
IS the router's output location. At `sync.py:585-588` the generator detects
`publish_src_real == publish_router_output`, prints "publish workflow is the
generated router itself (path='.'), skipping", and since no other project has a
`publish.yml`, `projects_with_publish` ends up empty and the gated router is
never generated. The pre-existing ungated `publish.yml` is left untouched.

Real-world consequence, observed twice in one release cycle: the Publish
workflow ran ungated on the `release` event and completed in ~30s, publishing
to PyPI while CI was still running — and once while CI ultimately FAILED. This
is precisely the race the publish gate exists to prevent, silently disabled for
this repo shape.

## Expected behavior

The generator must produce a gated publish workflow for the root publisher too:
either treat the root's publish as an inlined job in a freshly generated gated
router (replacing the stale ungated file), or inject the gate job + `needs`
wiring into the root `publish.yml` during sync. Silently leaving an ungated
publish workflow in place violates the publish-gating policy
(`publish_gate.build_router_gate_job` exists but is never invoked for this
shape).

## Affected

- `rlsbl/commands/monorepo/sync.py` (~585-588 self-exclusion branch)
- `rlsbl/commands/monorepo/publish_inline.py`
- A regression test for the single-releasable root-publisher shape.

## Effort

M. The gate machinery exists; the work is the root-publisher routing decision,
the three-way-merge/ownership handling for the existing `publish.yml`, and
tests.
