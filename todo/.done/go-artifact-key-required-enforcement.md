# Go `artifact` key: enforce required-no-default + fleet backfill + fix library verify template

Successor to the (now `.done/`) scaffold-go-library-publish-assumes-binary todo. The
template/detection/tests slice shipped in v0.105.0 (library template with
module-verification, no goreleaser; `_detect_go_artifact_kind` auto-detection on
first scaffold; `rlsbl/pipelines/go.py` template selection). What shipped VIOLATES
the original spec and the no-implicit-defaults policy, and the library verify
template is broken for monorepo tags. Decision 2026-07-17: enforce required +
backfill, all in one change.

## Problems

1. **Implicit default.** `pipelines/go.py:42` does
   `config.get("artifact", "binary")` — a Go library whose config lacks the key gets
   goreleaser (the exact original bug) with no error. `validate_pipelines_config`
   (`rlsbl/config.py:306-424`) has NO artifact check, in contrast to the npm
   `provenance` key which IS hard-required (`config.py:361-377`). The code's own
   docstring (`init_cmd.py:1471`, "No implicit default -- the key is always
   explicit") contradicts the implementation, and
   `tests/test_go_artifact_split.py:69-76` enshrines the default.
2. **No backfill path.** `_ensure_pipeline_config` returns early when `pipelines`
   already exists (`init_cmd.py:1476-1477`), so already-scaffolded projects never get
   the key added even on re-scaffold.
3. **Zero fleet adoption; two libraries silently wrong.** No fleet config declares
   `artifact` (verified 2026-07-17). The fleet has 9 binary Go projects and 2 Go
   library projects. One library's manually-edited gate-only publish router will be
   CLOBBERED BACK TO A GORELEASER JOB on its next monorepo sync (the router is
   generated; there is no customization for three-way merge to preserve). The other
   library has no go pipeline entry at all, so no proxy verification exists for it.
4. **Library verify template broken for monorepo tags.**
   `templates/go/publish-library.yml.tpl:36` extracts the version via
   `VERSION=${GITHUB_REF_NAME#v}`, which is garbage for releasable-format tags
   (`<name>@vX.Y.Z` — `#v` strips nothing). Additionally, a subdirectory Go module is
   only servable by the proxy via a subdir-prefixed tag (`<subdir>/vX.Y.Z` companion
   tags), which the verification must use.
5. **No GOPRIVATE stance.** The template hardcodes `GOPROXY=proxy.golang.org`; a
   private module can never verify. Expected posture: private repos use
   `publish_mode: "none"` (no publish job at all) — document this and hard-error
   clearly if a library verify job runs against an unservable module.

## Approved scope (one coordinated change)

1. Make `artifact` REQUIRED for `type: "go"` pipelines in
   `validate_pipelines_config`, mirroring the npm provenance pattern. Hard error
   naming the key, the two valid values, and the auto-detected suggestion.
2. Remove the `"binary"` default at `pipelines/go.py:42`.
3. Backfill all 11 fleet Go configs in the same sweep (identify via scan for go
   pipelines; 9 binary, 2 library), committed per repo with Autogenerated trailers.
   The library backfills must land BEFORE those repos' next monorepo sync.
4. Flip `test_default_to_binary_when_absent` to assert the hard error.
5. Fix the library template's version extraction to handle both plain `vX.Y.Z` and
   releasable `<name>@vX.Y.Z` tag formats, and verify against the correct
   proxy-visible tag (companion subdir tag for monorepo subdir modules).
6. Document the private-module posture (publish_mode none) in the template comment +
   pipelines docs.
