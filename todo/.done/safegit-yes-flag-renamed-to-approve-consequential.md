# safegit's `--yes` is gone; every rlsbl invocation of safegit is broken

Filed 2026-08-04, immediately after safegit adopted go-strictcli 0.29.0's redesigned
confirm protocol. This is a **live breakage**, not a future concern: `rlsbl commit` fails
today, and so does every rlsbl code path that shells out to safegit.

## What changed upstream

strictcli replaced the inferred "mutating command ⇒ prompt" rule. Commands now declare
themselves `consequential`, the framework prompts only for those, and the skip flag was
renamed `--yes` → `--approve-consequential`. **`yes` is now a banned flag name**: passing
`--yes` to a strictcli 0.29.0+ app is a hard error, not a no-op.

The consequence for safegit specifically:

| safegit command | Prompts now? |
|---|---|
| `commit` (and `commit --amend`), `push`, `pull`, `undo`, `unlock`, `config set`, `hook install`, `backup backup`, `backup restore`, the guarded passthroughs | **No.** They run bare. No flag of any kind. |
| `scrub file`, `scrub match`, `scrub run`, `author rewrite` | **Yes.** These four declare `consequential`. Non-interactive runs must pass `--approve-consequential`. |

## Where rlsbl breaks

1. **`rlsbl/utils.py`, `commit_files()`** — `run(tool, ["commit", "--yes", *trailer_args, "-m", message, "--", *files])`.
   This is the one that hurts: `rlsbl commit` (the documented way to commit machine-generated
   files with the `Autogenerated: true` trailer) fails outright with
   `error: unknown flag '--yes'` / `try 'safegit commit --help'`. `rlsbl changelog add`'s
   auto-commit hits the same path and degrades to `Warning: commit failed: ...` while still
   writing the JSONL, so the entry lands uncommitted and the working tree is left dirty.
   Fix: drop `--yes` entirely. `safegit commit` is not consequential and needs no flag.

2. **`rlsbl/commands/release_scrub.py`, `_build_safegit_args()`** — all three modes build
   `["scrub", "match"|"file"|"run", "--json", "--yes"]`. Fix: `--yes` → `--approve-consequential`
   in all three. The docstring paragraph explaining why `--yes` is explicit in every mode stays
   correct in substance; only the spelling changes (and these three commands are exactly the
   ones that still prompt, so the argument for passing it is stronger than before, not weaker).

3. **The author-rewrite path**, if `rlsbl` invokes `safegit author rewrite` anywhere outside
   tests — `author rewrite` is consequential too and needs `--approve-consequential`.

4. **Tests that assert the argv** — `tests/test_commit_files.py`,
   `tests/test_release_scrub_e2e.py`, `tests/test_release_reconcile_e2e.py`,
   `tests/test_scrub_detect_and_heal_e2e.py` all pin argv containing `--yes` and must be
   updated in the same pass.

Also worth a look while in there: `saferm` made the same move. Only `saferm purge` is
consequential now; `saferm delete` and `saferm undelete` run bare.

## Also: rlsbl's own confirm protocol has not migrated

Separately from the invocation breakage, rlsbl is itself still on the old regime — every
`mutating` rlsbl command prompts, so `rlsbl commit`, `rlsbl changelog add` and
`rlsbl check` all refuse non-interactively with `error: stdin is not interactive; pass
--yes to confirm`. That is the same 63%-of-commands over-prompting the redesign exists to
end. Bumping py-strictcli and declaring `consequential` on the genuinely dangerous rlsbl
commands (`release run`, `release yank`, `release scrub`, `release undo`, `monorepo mirror`)
is the matching half of this work. Doing both in one pass avoids touching the same call
sites twice.

## Effort

Item 1 alone is a one-line fix plus a test — minutes, and it unblocks `rlsbl commit` for
every repo in the fleet. Items 2-4 are another hour. The rlsbl-side confirm migration is a
half day including the judgement call on which commands are consequential.
