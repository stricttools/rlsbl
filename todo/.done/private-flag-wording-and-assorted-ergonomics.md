# `private` flag wording + assorted problems and nitpicks from heavy release use

A batch of findings from several days of intensive releasing across multiple consumer projects (three releases blocked mid-pipeline for different reasons, all eventually shipped). Items are independent — split freely at triage. Related, already filed separately: the npm `--provenance` scaffold todo.

## 1. `private` flag reads as repo visibility but means publish suppression (the headline item)

**Context.** `.rlsbl/config.json` supports `"private": true|false`. Per `config.py` and `release/validate.py` (`validate_config_integrity`), it means "suppress publishing to public registries" and the `private-publish-workflow` check requires a `private: true` project to have no publish workflows.

**Problem.** The name collides head-on with GitHub repo visibility. A consumer project with a PRIVATE GitHub repo that publishes PUBLIC packages must set `private: false` — maximally confusing. During a release, an agent flagged `private: false` on a private repo as a probable misconfiguration; only reading rlsbl source resolved it. The next agent (or human) may "fix" it and silently suppress publishing.

**Solutions.**
- (a) Rename to what it does: `suppress_publish = true` or `publish = false`, with a config-migration that hard-errors on the old key and names the new one. Pros: self-describing, one-time cost. Cons: touches all consumers (mechanical).
- (b) Keep the key, document loudly in config docs + the check's error text ("this is NOT GitHub visibility").
- (c) Both: rename AND make the `private-publish-workflow` check message explain the semantics.
Recommendation: (a)/(c). Effort: small-medium (rename + migration + docs + check text).

## 2. Scaffold three-way merge can silently revert deliberate local decisions

**Context.** Scaffold-managed workflow files are three-way merged on re-scaffold (bases in `.rlsbl/bases/`). A consumer deliberately edited its npm publish step (a decision with a written commit message); a later scaffold update rewrote that whole region (a job grew ~5x), the merge conflicted, and the resolution went to the template side — reverting the deliberate local decision. Every publish then failed for weeks until rediscovered.

**Problem.** There is no way to declare "this divergence is a permanent local decision." Load-carrying local edits to scaffold-managed files eventually lose a merge, and the loss is silent.

**Solutions.**
- (a) Move known decision points into config (the already-filed provenance todo is one instance): scaffold generates the file correctly per-project, so there is no divergence to lose. Pros: eliminates the class. Cons: only covers anticipated knobs.
- (b) A scaffold "local-decision markers" mechanism: an annotated comment block (`# rlsbl:keep`) that re-scaffold refuses to auto-resolve against, hard-erroring with both versions shown. Pros: general. Cons: new mechanism.
- (c) At minimum: after re-scaffold, print a diff summary of every hunk where the merge chose the template over a local edit.
Recommendation: (a) for known knobs + (c) as a cheap universal backstop. Effort: (c) small, (a) per-knob, (b) medium.

## 3. Release pipeline aborts on dirty files its own steps generate

**Context/problem.** `rlsbl release run --no-allow-dirty` runs strictcli schema dump and `selfdoc gen --no-auto-commit`, which modify generated files; the pipeline then aborts on the dirty tree it just created. In four releases in a row the operator loop was: run → abort → `rlsbl commit` the generated files → run again. The tool creates the condition it then refuses.

**Solutions.**
- (a) The pipeline auto-commits outputs of its own generation steps (they are machine-generated; `rlsbl commit` semantics with the Autogenerated trailer), then proceeds. Dirtiness from anything OTHER than its own steps still aborts.
- (b) Generation steps run in check-only mode during release and hard-error telling the user to run generation before releasing.
Recommendation: (a) — it matches what every operator does by hand anyway, with no loss of safety since the auto-commit is scoped to the pipeline's own outputs. Effort: small-medium.

## 4. Duplicate CI runs on one commit can deadlock the publish gate

**Context.** A release commit triggered two CI runs on the identical SHA (branch push + tag push events). One run was fully green; the other flaked red. The scaffolded publish gate aggregates ALL matching check-runs on the commit, so the red duplicate blocked publish forever — re-running the red run kept flaking, and the green run's existence counted for nothing.

**Problem.** Duplicate-event runs are pure redundancy with veto power. The only rule-compliant recovery was a patch release.

**Solutions.**
- (a) Scaffold CI `on:` filtering so one SHA triggers one run (e.g. skip tag-push runs when the branch push already covers the SHA, or `concurrency` groups keyed on SHA).
- (b) Gate semantics: accept the commit if ANY complete run of the required matrix is fully green (per-run evaluation instead of union-of-all-runs).
Recommendation: (a) — removes the redundancy at the source; (b) changes gate semantics and needs care not to weaken it. Effort: small.

## 5. `rlsbl release undo` ends in a manual `git push`

**Context/problem.** The documented undo flow reverts commit + tag + GitHub Release but requires the operator to push manually afterward — in an ecosystem whose rule is "never push manually; all pushes happen through rlsbl." The one sanctioned recovery tool ends in a rule violation, so agents refuse to use it and route around (patch releases even where undo was arguably cleaner).

**Solution.** `rlsbl release undo` performs the push itself (it is exactly as tool-mediated as `release run`'s push), with `--dry-run` support. Effort: small.

## 6. No sanctioned "republish" path when the git side landed but registries missed

**Context.** Twice, a release completed its git side (tag pushed, GitHub Release created, JSONL finalized) but the CI-gated registry publish failed (an environment flake; a workflow misconfiguration). The fix needed a new commit, the tag is immutable, and the recovery is a patch release whose only content is the CI fix.

**Problem.** The changelog user-facing gate then hard-errors: a pure-recovery release has no user-facing entries. Operators must reach for the "build changes that broke user installs count as user-facing" carve-out and write a somewhat contorted entry. It worked, but the tool has no honest vocabulary for "vX.Y.Z never reached the registries; vX.Y.Z+1 publishes the line."

**Solutions.**
- (a) A `republish` release kind in the release file: requires that the previous tag's registry artifacts are absent (verified), waives the user-facing-entry requirement for that release only, and auto-writes a standard "publishes the vX.Y line" changelog entry.
- (b) Keep the carve-out but document the recovery playbook explicitly (release docs section: "when publish fails after tagging").
Recommendation: (a); it's a real, recurring state with well-defined preconditions the tool can verify. Effort: medium.

## 7. `changelog add` behavior for one-commit-in-multiple-entries is inconsistent (verify)

**Context/problem.** The data model documents that one commit MAY appear in multiple entries (bounded by `max_entries_per_commit`). In one project, adding a second entry referencing an already-covered commit succeeded with a benign warning; in another (days later, possibly a newer rlsbl), an agent reported `changelog add` REFUSING the second entry outright and merged two logically distinct changes into one entry to proceed. If add now hard-blocks, it contradicts the documented model; if the agent misread a warning as refusal, the message text is ambiguous enough to cause wrong behavior.

**Solution.** Verify current behavior; either allow-with-warning consistently (respecting the bound) or update the documented model; make the message unambiguous about whether the entry was written. Effort: small.

## 8. Non-gating FAILs in `check --all` erode the meaning of FAIL

**Context/problem.** `rlsbl check --all` prints FAIL for diagnostics that gate nothing (lint findings in helper scripts, circular-deps informational cycles) alongside FAILs that abort releases. Operators and agents learn to pattern-match "these FAILs are ignorable," which is exactly the reflex the ecosystem's hard-error philosophy exists to prevent — one day a gating FAIL gets ignored by habit.

**Solution.** Distinct verdict vocabulary by consequence: FAIL only for release/push-gating checks; non-gating diagnostics report as WARN/INFO (or a `--strict` mode promotes them). Effort: small.
