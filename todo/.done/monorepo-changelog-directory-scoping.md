# Monorepo changelog coverage should scope to package directory

## Problem

In a monorepo, `rlsbl check --tag changelog` (coverage check) requires every non-exempt commit in the unreleased range to have a JSONL entry — regardless of whether the commit touches files in the package's directory.

A package like `alerting/` that only had 1 file change (build backend standardization) sees 205 commits in its range and reports 46 uncovered. These 46 commits modified files in completely unrelated packages (cli/, cloudflare/, root config files, etc.).

This makes changelog coverage impractical for monorepos:
- 50 packages × ~46 uncovered commits = ~2300 non-user-facing entries needed
- The entries add no value — they describe changes that don't affect the package
- Generated CHANGELOGs would correctly show "No user-facing changes" but the coverage machinery requires the entries to exist

## Expected behavior

For monorepo packages (those listed in `workspace.toml`), the coverage check should only require JSONL entries for commits that modify files within the package's directory tree.

Example: if `alerting/` has tag `alerting@v0.1.0`, the coverage check should:
1. Compute range: `alerting@v0.1.0..HEAD`
2. Filter to commits touching `alerting/**`
3. Only require entries for those filtered commits

Commits that only touch root files, other packages, CI configs, etc. should not need coverage in the `alerting/` changelog.

## Current workaround

None practical. The only option is to bulk-add ~46 non-user-facing entries per package (scripted), which creates ~2300 entries of noise across the monorepo.

## Context

Discovered in the WWW monorepo (50 packages, all at v0.1.0, 54 unreleased commits). Packages released earlier in the v0.1.0 batch see even more commits (205 for alerting) because their range starts earlier, including all the autogenerated release commits for packages released after them.

The autogenerated commit auto-exemption works correctly (155 skipped for alerting). The issue is only with the remaining non-exempt commits that don't touch the package.

## Root-level coverage

Commits that ONLY touch root-level files (`.gitignore`, `www.toml`, `selfdoc.json`, etc.) should only need coverage in the root package's changelog. The root package is the catch-all for cross-cutting changes.
