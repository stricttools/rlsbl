# First-class hotfix release type

## Problem

The `changelog-user-facing` check requires every release to have at least one user-facing entry. This correctly prevents empty releases but also blocks hotfixes — urgent releases that fix something broken (CI, deploy config, scaffold artifacts) without changing user-facing CLI/API behavior.

Currently, the only way to release a hotfix is to write a user-facing changelog entry describing an infrastructure fix. This feels like gaming the guardrail rather than satisfying it. The CLAUDE.md rule "never fabricate a user-facing entry to bypass the user-facing requirement" directly conflicts with the need to ship urgent fixes.

A hotfix is inherently user-facing — if it weren't affecting users (or CI, or deployment, or something visible), it wouldn't be worth fixing immediately. The urgency is what makes it a hotfix, and urgency implies impact. The guardrail should recognize this.

## Proposed solution

Add a `hotfix` release type alongside the existing `patch`/`minor`/`major` bump types. When the release file declares `bump = "hotfix"`:

1. The `changelog-user-facing` check is satisfied by the release description alone (no individual user-facing entries required)
2. The version bump is always patch (hotfix is a subset of patch)
3. CHANGELOG.md generates a `### Hotfix` section using the release description instead of grouped entries
4. The release description is mandatory (must explain what was broken and what the fix is)

This shifts the intent check from "does this have user-facing entries" to "did the author consciously choose hotfix mode and explain why" — same protection against empty releases, without forcing artificial changelog entries.

## Example

```toml
# .rlsbl/releases/unreleased.toml (or monorepo equivalent)
bump = "hotfix"
description = "Fix broken root CI workflow generated by scaffold for workspace roots."
```

Produces in CHANGELOG.md:
```markdown
## 0.3.1

### Hotfix

Fix broken root CI workflow generated by scaffold for workspace roots.
```

## Affected files

- `rlsbl/commands/release/validate.py` — accept `hotfix` as bump type, enforce patch semantics
- `rlsbl/checks/changelog.py` — `changelog-user-facing` check: pass when bump is hotfix and description is non-empty
- `rlsbl/changelog/generate.py` — render `### Hotfix` section from release description
- `rlsbl/commands/release/execute.py` — map hotfix to patch for version arithmetic
