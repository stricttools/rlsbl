# The workspace changelog roll-up emits one H1 per releasable

The combined root `CHANGELOG.md` that `generate_workspace_changelog` writes for
an explicit-releasable monorepo is not a single Markdown document. It is N
documents concatenated, each with its own top-level heading.

## The problem

`rlsbl/changelog/home.py:generate_workspace_changelog` reads each releasable's
canonical `CHANGELOG.md`, calls `_strip_canonical_header` to remove that file's
generated-file comment and its `# Changelog` H1, and re-emits the remainder
under a fresh `# <releasable name>` heading:

```python
sections.append(f"# {rel.name}\n\n{body}\n")
```

A three-releasable workspace therefore produces a root file with three `# `
headings. The per-releasable files it was built from each carry exactly one, so
the same generator produces two outputs with contradictory heading contracts:
the canonical file is a document, the roll-up is a stack of documents.

Every consumer that treats the root `CHANGELOG.md` as one document sees this:

- a Markdown linter enforcing single-H1 (a near-universal rule) fails it;
- a documentation generator that renders the root changelog as a page rejects
  it, or renders a page with three competing titles;
- an HTML outline built from the file has three top-level entries and no
  document title;
- a reader skimming a rendered version has no heading that says what the file
  is; the first thing they see is a releasable's name.

Nothing downstream can repair it, because the information that these are
sections of one changelog was never encoded.

## Why the current shape is wrong rather than merely unusual

The roll-up's whole reason to exist is to answer "what changed in this
workspace" in one file. That claim needs a document heading. The current output
asserts the opposite: three peers with no relationship stated.

The version sections inside are `## X.Y.Z`, correct beneath a per-releasable H1
and correct nowhere else — which is the tell that the sections were lifted
without being re-levelled for their new home.

## Proposed fix

Give the roll-up one H1 and demote everything below it by one level:

```
<!-- Generated by rlsbl ... -->

# Changelog

## <releasable name>

### 0.4.1

#### Features
- ...
```

That means `generate_workspace_changelog` must re-level each section's body,
not just re-head it: `##` version headings become `###`, and the `### Breaking`
/ `### Features` / `### Fixes` group headings inside them become `####`.

### Options

| Option | Pros | Cons |
|---|---|---|
| Re-level in the roll-up generator (regex or line rewrite over the stripped body) | Localized to one function; per-releasable files are untouched; no new config | A textual transform over generated text; must not touch `#` inside fenced code blocks in an entry description |
| Render the roll-up from the JSONL sources at the correct depth, instead of concatenating rendered files | No re-levelling needed — depth is a render parameter; structurally correct by construction | Larger change; the roll-up currently reuses the canonical files as its input, so this needs the renderer to take a heading-offset |
| Leave three H1s and document them as intended | Zero work | Leaves the file unrenderable as a page and unlintable; the same generator keeps contradicting itself between its two outputs |

The second option is the more correct one: a heading offset threaded through the
renderer makes the malformed shape unrepresentable, where a post-hoc re-level
can always be defeated by an entry whose description contains a fenced block
with a `#` line. If the renderer already takes its heading levels from one
place, that is a small change; if levels are hardcoded in several places, the
first option is the honest interim and the second is the follow-up.

Either way, treat the fenced-code case explicitly: a changelog entry may quote
Markdown, and a naive `^#` rewrite corrupts it.

## Affected files

- `rlsbl/changelog/home.py` — `generate_workspace_changelog`,
  `_strip_canonical_header`
- whatever module renders a version's Markdown from JSONL (the source of the
  `## X.Y.Z` and `### Breaking|Features|Fixes` levels), if the heading-offset
  route is taken
- callers that regenerate the roll-up and would rewrite existing files:
  `rlsbl/commands/changelog_cmd.py`, `rlsbl/commands/undo.py`
- tests covering roll-up generation

## Migration

Existing root `CHANGELOG.md` files are generated, so they heal on the next
`rlsbl changelog generate` or release. No manual step, but the first
regeneration produces a large diff on every monorepo — worth saying so in the
changelog entry.

## Effort

Small-to-medium. The re-level route is an afternoon including tests. The
heading-offset route depends on how many places hardcode the levels; likely a
day if the renderer needs a new parameter threaded through it.
