# Workspace snapshot

## Context

AI agents and humans working in a monorepo need to understand its structure: what packages exist, what each does, what depends on what, what version each is at. Currently this requires reading N manifest files and mentally assembling the graph. There's no single artifact that summarizes the workspace state.

## Decisions

- **Name**: workspace snapshot (not cache -- it's a committed artifact, not a performance optimization).
- **Location**: `.rlsbl-monorepo/snapshot.json`.
- **Format**: JSON only (AI-first; LLMs parse JSON natively).
- **Regeneration**: on demand via `monorepo snapshot` + auto-regenerated during release.
- **Descriptions**: manually authored in workspace.toml (`description` field per project). Not auto-extracted from READMEs or manifests.
- **Committed to the repo**: always. Auto-committed with `Autogenerated: true` trailer.

## Schema

```json
{
  "generated_at": "2026-05-20T12:00:00Z",
  "package_count": 41,
  "packages": {
    "models": {
      "path": "packages/models",
      "target": "dart",
      "version": "2.1.0",
      "description": "Core data models and value objects",
      "deps": ["schema", "infra"],
      "rdeps": ["marketplace_contract", "payments_contract", "flow_order"],
      "library": true,
      "test_only": false
    }
  },
  "graph": {
    "leaf_nodes": ["schema", "infra"],
    "root_nodes": ["app", "conformance"],
    "max_depth": 5,
    "topological_order": ["schema", "infra", "models", "..."]
  }
}
```

### Per-package fields

| Field | Source | Description |
|-------|--------|-------------|
| `path` | workspace.toml | Relative path from repo root |
| `target` | `detect_targets()` | Primary target type |
| `version` | target `read_version()` | Current version |
| `description` | workspace.toml `description` field | One-line description (manually authored) |
| `deps` | `WorkspaceGraph` | Direct intra-workspace dependency names |
| `rdeps` | `WorkspaceGraph` | Direct reverse dependency names |
| `library` | workspace.toml `library` field | Whether it's a shared library |
| `test_only` | workspace.toml (new field?) | Whether it's test infrastructure |

### Workspace-level fields

| Field | Source | Description |
|-------|--------|-------------|
| `generated_at` | current time | ISO 8601 timestamp |
| `package_count` | count of packages | Total packages |
| `leaf_nodes` | graph analysis | Packages with no intra-workspace deps |
| `root_nodes` | graph analysis | Packages nothing depends on |
| `max_depth` | graph analysis | Longest path in the DAG |
| `topological_order` | `topological_order()` | Release order |

## Command

`monorepo snapshot [--check]`

- No flags: regenerate snapshot.json and commit it.
- `--check`: verify that snapshot.json is up-to-date (exit 1 if stale). Useful in CI.

## workspace.toml description field

Requires the `save_workspace()` round-trip fix first. Then add a `description` field per project:

```toml
[[projects]]
path = "packages/models"
name = "models"
description = "Core data models and value objects"
library = true
```

`description` is optional. Packages without it get `null` in the snapshot.

## Staleness

The snapshot is a point-in-time artifact. It goes stale when:
- Packages are added/removed
- Dependencies change
- Versions are bumped

Staleness is acceptable between releases (the snapshot is regenerated on release). `monorepo snapshot --check` can be used in CI to enforce freshness if needed.

## Effort

Small-medium. Most data is already computed by `monorepo status`. The new work is serializing it to JSON, adding the `description` field to workspace.toml, and wiring auto-regeneration into the release flow.
