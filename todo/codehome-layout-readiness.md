# Readiness for the `.codehome/` layout migration, and what it exposed

Filed from a read-only assessment of rlsbl and safegit 0.29.0 against the
planned repository-data layout program. Every finding was verified against
the working trees at filing time; symbol names are the references and line
numbers are omitted on purpose. Measurements are marked as measured at
filing time and drift.

This file is a handoff. It records what the assessment established, the
work it implies for rlsbl (some of it useful today, before any migration),
the corrections the layout program's own design needs, and the decisions
the owner must make before anything is built. Nothing is decided unless
the "Open decisions" section says so.

## Context

The layout program moves every repository's tool state directories
(`.rlsbl/`, `.rlsbl-monorepo/`, and the other tools' dot-directories, plus
docs and todo content) into one function-named directory per repository,
`.codehome/<function>/`, with state keyed by DECLARED releasable or
project names in filenames, a small per-directory manifest declaring each
directory's nature (handwritten or generated; committed or not), and a
`rlsbl migrate-layout` command shipping in the same release that flips the
read path. rlsbl owns most of the moved files and the workspace
declaration. The migration design is a pure-move commit made with
`safegit mv` (which mints declared subtree move records) followed by a
content-rewrite commit.

The assessment tested eleven proposed ways safegit and rlsbl could support
that program. What follows is the rlsbl half: facts, then work, then
decisions. The safegit half is filed in safegit's own todo directory.

## Facts established at filing time

### Release records and path-keyed state

- The release archives' `tree_hashes` are keyed by MEMBER path (`"."`, or
  each member's path — `release_commit_tree_hashes` in
  `commands/release/execute.py`), and their values are tree objects at
  `candidate_sha`, historical facts no later commit can change. The dotdir
  migration moves no member path. No reader compares `tree_hashes` against
  HEAD: the complete reader set is `release_commit_remap.py` (recomputes
  at the rewritten historical commit), `monorepo/extract_cmd.py` and
  `monorepo/absorb_cmd.py` (recompute at the filtered commit and rewrite
  the key through `_dest_release_commit_path` from an explicit declared
  destination), and the writers. `release_reconcile.py`, `mirror_cmd.py`,
  `mirror_publication.py`, `commands/undo.py`, `release_record.py` and
  `tag_explanation.py` contain no reference; `ReleaseRecordEntry` does not
  carry the field. The migration does not stale `tree_hashes`.
- The path-keyed state the migration DOES stale is small:
  `managed-files.json` keys (repository-relative target paths such as
  `.rlsbl/changes/unreleased.jsonl` and `.rlsbl/lint/*.toml`) — rewritten
  wholesale on every `rlsbl scaffold` (`save_managed_files`), with orphans
  of vanished paths skipped; and `.rlsbl/bases/<target-relpath>` — stale
  twice over, because the directory moves AND its inner filenames encode
  target paths. Transition-record endpoints, scrub archives (SHAs and tag
  names only), `workspace.toml` member paths, `subtree_remote`,
  `install_paths`, external-check paths and the local overlay file are
  member-path or out-of-repo and unaffected. Everything else is a code
  constant (measured at filing time: several hundred `.rlsbl` string
  occurrences across the package), which is the migrator's rewrite job.
- `_reconstruct_base_from_history` in `commands/init_cmd.py` runs
  `git log --grep="rlsbl scaffold" -n1 -- <target>` with no rename
  awareness, so after any managed-file relocation it returns nothing at
  the new path; the base sweep in the scaffold flow deletes every base
  whose key is absent from the fresh hash set; and
  `_require_healable_bases_dir` then hard-errors on a project that has
  `managed-files.json` and no `bases/`. This is live today for any
  relocation, migration or not.
- `.rlsbl/changes/.validated` is a tracked file (a cache holding a HEAD
  SHA, rewritten on nearly every validation).
- `.rlsbl/changes/` holds four kinds of file in one directory: released
  `X.Y.Z.jsonl` (chmod 444 by `finalize_version`), released `X.Y.Z.md`
  (freely regenerated by `changelog generate`, never chmodded),
  `unreleased.jsonl` (hand-appended), and the tracked `.validated` cache.
  The layout program's authorship axiom (a directory is entirely
  handwritten or entirely generated) is already violated by this directory
  today, and its planned `changelogs/` inherits the violation unless the
  layout splits it.
- No check detects a hand edit to a released JSONL or a release archive.
  Every changelog check reads `read_unreleased` only
  (`checks/_common.py`); the `.validated` cache keys on HEAD and
  `unreleased.jsonl`'s mtime; the chmod 444 is the sole guard, git does
  not store it, and a fresh clone materializes the files writable. A hand
  edit would be propagated faithfully into `CHANGELOG.md` by
  `changelog generate`. The existing archive fields cannot answer: the
  finalized `X.Y.Z.jsonl` is created at release step 17 while
  `candidate_sha` and `tree_hashes` name the step-15 commit that does not
  contain it.
- Historical trees' release archives keep a stale `candidate_sha` after a
  scrub: the archives are not in the `--remap-shas-in` glob list, and
  `release_commit_remap.py` repairs the working tree only, from safegit's
  journal.

### Attribution

- Commit-to-project attribution funnels through two entry points in
  `ownership.py` — `owner_of` (most-specific declared path wins; the root
  member is the residual) and `OwnershipScope.claims` — plus
  `tool_owned_rule` and the static tool-owned sets. `state_dir_releasable`
  already IS a reverse key map: it parses
  `.rlsbl-monorepo/releasables/<name>/...` to `<name>`, and
  `OwnershipScope.state_dirs` turns that into a scope claim.
  `router_filters.py`'s `_finalize_artifact` is the corresponding
  hand-built forward key map for the one existing keyed root path.
- Every attribution consumer (the `changelog add` scope check and remedy
  text, packages derivation, the range/coverage/orphans checks, the
  changelog-only exemption, prepush coverage and test dispatch,
  `monorepo impact`, `unreleased`, `status`, `monorepo status`,
  `monorepo release init`, `release undo`'s overlap check, cwd
  resolution) reaches ownership through those two entry points. The
  router derives globs and needs its own small change. The release flow's
  range pin compares SHAs and does no attribution.
- The function the layout program calls `file_matches_project` does not
  exist under that name.
- rlsbl reads trailers in two ad hoc ways that disagree:
  `changelog/exemptions.py` uses git's trailer parser
  (`%(trailers:key=Autogenerated,valueonly)`, any subprocess error means
  "not exempt"); `monorepo/absorb_cmd.py` scans lines with `startswith`,
  which matches inside a body.
- Three commit sites write release state without the `Autogenerated:
  true` trailer that `commit_files` adds by default: the scrub repair
  commit and the scrub metadata commit in `commands/release_scrub.py`
  (the latter carries `Scrub-remap:` instead), and the reconcile commit
  in `commands/release_reconcile.py`. They are coverage-exempt anyway
  through the tool-owned path rule, so this is an inconsistency, not a
  defect.

### Renames

- `rename-releasable` (`commands/monorepo/releasable_rename.py`) rewrites
  `workspace.toml` in place, moves the state directory with
  `effects.rename` (a plain `os.rename`), deletes the tracked `.validated`
  and the publish-router cache, re-syncs, and commits once through
  `commit_files_if_changed` (`safegit commit --trailer "Autogenerated:
  true"`), then appends a `ReleasableRenameEvent` to the repository-scoped
  transition record and, for `{name}` tag formats, creates and pushes a
  boundary alias tag recorded as a `BoundaryAliasEvent`.
- That commit records ZERO safegit move records today. The tracked
  `.validated` is deleted in the same commit with no matching add, which
  fails safegit's subtree-collapse predicate; the per-file pairs then
  exceed safegit's inference cap (twenty records per commit, counted after
  collapse; measured at filing time, rlsbl's own `changes/` holds several
  hundred tracked files), and past the cap safegit records none. The
  directory move is therefore recorded nowhere.
- `ReleasableRenameEvent` carries `old_name`, `new_name`, `reason` — no
  directory-move part. A move record would be purely additive.
- There is no member-rename command; per-member state lives under the
  member's PATH, so a member rename moves no files today.

### safegit facts the migrator depends on (verified in safegit 0.29.0)

- `safegit mv` mints one DECLARED record per pair regardless of file
  count, and declared records are never subject to the inference cap.
  Inference (a bare `git mv` plus `safegit commit` without `--moved`) is
  structurally unreliable for rlsbl's directories: measured at filing
  time, `.rlsbl/bases/` stores byte-identical copies of the files it is a
  base for, so every base file fails safegit's unique-blob fence.
- Two pairs in one `mv` (or one `commit --moved`) are refused when their
  sources nest, their destinations nest, or they chain. A subtree pair and
  a file pair placed under the same destination directory are refused as
  a nested destination. A destination whose parent does not exist needs
  `--create-missing-directories`.
- `mv`'s dirty check is disk-content-versus-HEAD for the tracked paths
  under the moved prefixes and nothing else: staged-only changes,
  untracked files, deletions and mode changes pass. `mv` commits each
  entry's mode from HEAD's tree entry, never from disk, and git records
  only the executable bit — a 444-versus-644 difference is not a tree
  fact, so no commit can make a clone materialize a file read-only.
- `mv`'s filesystem half renames the directory whole: untracked and
  gitignored content (`in-progress.json`, build output) travels silently
  and is un-ignored at the new path until the ignore rules are rewritten.
- `safegit undo` moves the ref and reconciles the index; it never writes
  the working tree. It refuses without `CLAUDE_CODE_SESSION_ID` (unless
  `--bypass-session`, which would also undo other sessions' commits), and
  refuses when any commit safegit did not make sits in the range. Exit
  codes: operation in flight 5, CAS exhaustion 7, operation lock 8, move
  not borne out 19 (path list on stderr only; the `--json` document has a
  null payload), commit-stands-with-residue 26.
- A move record cannot be declared retroactively; moves made before
  safegit 0.29.0 — including every monorepo conversion that relocated
  `.rlsbl/changes/` via `os.rename` — are permanently unrecorded, so a
  scrub-side path translation reaches only post-0.29.0 moves.
- rlsbl's safegit floor is scrub-scoped: `SAFEGIT_MIN_VERSION = (0, 28,
  0)` in `commands/release_scrub.py`, alongside the only `--json` parser,
  `_parse_safegit_envelope` (interface version 2, no dual recognition).

## Work items

### 1. An integrity check for released changelog files and archives (useful today)

Record each released JSONL file's blob SHA in that version's release
archive at finalization, and add a `changelog-released-immutable` check
(project and preflight tags) comparing the on-disk blob against the
recorded one. `changelog amend`, `changelog edit`, `changelog remove` and
`changelog remap` update the recorded hash inside their existing
unlock-rewrite-relock (`writable_jsonl`); `release undo`'s un-finalize
clears it. Consider the same for the archive files themselves (a recorded
hash for the archive cannot live in the archive; a companion field in the
next archive or a repository-scoped record is the design question).

This closes the observed gap with no dependency on the layout program, on
a manifest, or on safegit. Red-green: hand-edit a released JSONL in a
fixture, assert the check reds; restore, assert it clears; run each
mutating changelog command, assert the recorded hash follows.

### 2. `rename-releasable` declares its state-directory move (useful today)

The instrument is `safegit commit --moved
'<workspace-dir>/releasables/<old>/ -> <workspace-dir>/releasables/<new>/'`
on the single rename commit — not `safegit mv`, because the rename is not
a pure move (`workspace.toml` changes in the same commit) and two commits
would leave an intermediate tree that every rlsbl load path refuses. The
declared bear-out check is presence-only, so the `.validated` deletion in
the same commit is harmless.

Concretely: thread an optional list of `(old, new)` move pairs through
`commit_files` and `commit_files_if_changed` in `utils.py`, emitting one
`--moved` per pair when the commit tool is safegit; pass the subtree pair
from `_apply_local_rename`; promote `SAFEGIT_MIN_VERSION` out of the scrub
module into a shared module and raise it to `(0, 29, 0)`, since move
records now ride ordinary commits. Under the keyed layout the same
mechanism carries N pairs, one per function directory holding the
releasable's name; the migrator, not this command, owns enumerating them.

The alias tag and the transition event stay: the tag serves the tag
namespace, the event is rlsbl's own fact that stops
`refuse-identity-mismatch` and explains historical `<old>@v*` tags, and
the move record says where files went. Three instruments, three
questions, no overlap. Inferring a rename FROM move records is forbidden —
that would be the duplication.

Tests: red-green for the missing record (a fixture over the cap with the
tracked `.validated`; assert no `Moved:` trailer, fix, assert one subtree
record with an empty origin slot, parsed with the real grammar rather than
a substring); the crash-healing tests must not emit a second `--moved`
or fail bear-out when the old prefix is already gone; dry-run renders the
pair and commits nothing (`commit_files` already skips the stageable
filter under a preview; the `--moved` path needs the same treatment);
both trailers present on the commit.

A `rename-member` sibling is needed only once member state is keyed by
name; when that comes, factor the rename preflight helpers rather than
duplicating them.

### 3. Rename-aware base reconstruction, and base-path rewriting in the migrator (useful today)

Make `_reconstruct_base_from_history` follow renames, and make the
migrator rewrite `.rlsbl/bases/` inner key paths as part of the move so
reconstruction is never needed for the migration. Red-green: relocate a
managed file without rewriting its base path, assert
`_require_healable_bases_dir` errors; fix; assert it clears and a
customization is preserved through a re-scaffold.

### 4. The reverse key map in `ownership.py` (ships in the layout-flip release)

Post-migration, a commit touching only a keyed root file such as
`.codehome/changelogs/<releasable>/unreleased.jsonl` attributes to the root
member. That is a SILENT coverage pass in prepush (a dev-node root is
skipped) and a HARD error in `changelog add` run from a member directory
(the scope's state directories carry the old spelling; the commit claims
nothing) — same cause, two symptoms.

The work generalizes what exists: a function-directory vocabulary table in
`workspace_types.py` (directory name, key namespace — releasable or
project — and whether it is tool-owned for coverage); the tool-owned sets
rewritten to enumerate function directories one by one (a blanket
`.codehome/` rule would exempt todo, docs and post content from coverage);
`state_dir_releasable` generalized to a vocabulary-driven
`keyed_path_owner(path) -> (namespace, key)`; `OwnershipScope.state_dirs`
generalized to keyed claims per namespace; `owner_of` consulting the key
map before the root residual; `_finalize_artifact` generalized to the
keyed set as selective literal paths, never directory-wide globs. The
attribution consumers need no caller edits.

The rejected alternative, recorded so it is not re-proposed: a `Project:`
or `Releasable:` trailer minted at commit time. It is a snapshot of a
derivable fact, falsified by `rename-releasable`, `absorb`, `extract` and
any `workspace.toml` edit with no commit-message remapper anywhere; no
minting point is universal (safegit would have to learn the workspace
declaration against its own subset law; a per-clone `commit-msg` hook
covers no history and no other machine); and a trailer present on some
commits forces a dual-mode reader at every site. The one underivable case
is an empty commit, which needs no entry. Measured at filing time, the
safegit session trailer covers nearly every commit in two sampled
monorepos — which is what made the idea look viable.

Preconditions: the manifest's filename and keys; both key namespaces
declared in the workspace file; the load-time name grammar (a derived key
can be `.` today, which would make the reverse parse a path escape).

Tests: red-green for the silent pass and for the hard block; a
releasable-keyed and a project-keyed directory sharing one spelling
resolve to different owners; disk keys not among declared names is a load
error; grammar refusals; non-blanket exemption; router freshness;
scope-then-exempt order identical across `unreleased`, `status`,
`monorepo status` and `check --tag changelog`; remedy truthfulness; rename
invariance (after a rename every historical commit resolves under the new
name with no history rewrite).

Side work: unify the two trailer readers on git's parser.

### 5. Migrator obligations established by the safegit facts

`rlsbl migrate-layout` must:

- Move with `safegit mv` and declared subtree pairs, never inference.
- Split the pure move into as many `mv` commits as destination nesting
  requires: a destination directory that receives from more than one
  source (a subtree and a single file, or two subtrees) cannot be filled
  in one invocation. Either the layout gives each destination directory
  one source, or "two commits per repo" becomes "N move commits plus one
  rewrite commit". Keep every pair disjoint on both sides.
- Introduce the per-directory manifests in the rewrite commit; `mv`
  cannot add files.
- Pass `--create-missing-directories`; start from a clean tree; run the
  `--dry-run` form first (it performs the full dirty check but takes no
  lock, so it is a snapshot, not a reservation).
- Write the new `.gitignore` rules to disk BEFORE staging the rewrite
  commit with directory arguments, or name every file explicitly;
  otherwise build output and `in-progress.json`, un-ignored at their new
  paths, get committed.
- Set a stable `CLAUDE_CODE_SESSION_ID` for the run; never pass
  `--bypass-session`; make no commit of any kind between its own commits
  (no `changelog add` auto-commit, no docs regeneration auto-commit); no
  scrub in the window.
- Own the working-tree half of any rollback: two undos restore the
  history, not the tree, and a retry after an undo is refused by `mv`
  because the moved paths then carry uncommitted content. The inverse
  moves are derivable from the commit's own records; restoring the
  rewritten files' bytes from HEAD's blobs is a designed operation that
  needs the owner's ruling against the fleet's ban on `git restore`-class
  commands.
- Treat exit 26 as commit-stands; parse stderr for exit 19; treat 5 and 8
  as come-back-later.
- Drop the "heal chmod-444 permission drift" claim: git does not store it
  and no commit can heal it. Anything that wants read-only files in a
  fresh clone chmods after checkout.
- Rewrite `.rlsbl/bases/` inner paths (item 3) and regenerate
  `managed-files.json` through scaffold.

### 6. Mirror model under the keyed layout (design owed)

A mirrored releasable's mirror is the subtree split of its member path
overlaid with a scaffold layer whose owned-path set is a pinned list in
`mirror_cmd.py` naming `.rlsbl/` and `.github/` prefixes. If per-member
`.rlsbl/` state moves to the repository root under `.codehome/`, the split
no longer carries it and the pinned list no longer matches, so the
mirror's `contract-violated` refusal fires. This needs a design, not a
heal.

### 7. Consumer-side adoption of two planned safegit commands

safegit's todo proposes a read-only move-record projection command and a
read-only undo recoverability probe, each emitting a `--json` document
with a declared schema. When they ship: lift `_parse_safegit_envelope`
out of the scrub module into a shared helper with the promoted floor
(item 2); consume the probe from `rlsbl commit`'s reversibility
declaration; use the projection command in the rename tests (item 2) to
assert a file's old path projects to its new one, instead of asserting
record shape by hand. Do not reimplement the record grammar in Python.

### 8. Scrub after the migration

`changelog_remap_globs` derives its globs from the same enumeration as
hash validation, on purpose, so remap coverage and validation coverage
cannot diverge. After the migration it emits new-layout globs; safegit's
proposed scrub-side path translation would carry them back through the
migration's recorded moves to pre-migration trees. That reaches only
moves recorded by safegit 0.29.0 or later. The monorepo conversions that
relocated `.rlsbl/changes/` before records existed are out of reach
forever; for them the options are to accept the reported dangling hashes
in historical trees (the current state) or to add a range-scoped glob
flag on rlsbl's side. Rejected: discovering the remap set from
per-directory manifests read out of each historical tree (it would split
the one enumeration into two authorities and make a documentary manifest
decide what a destructive rewrite edits; safegit's todo records the
reasoning and a safegit-owned alternative).

### 9. Three commits without the `Autogenerated: true` trailer (consistency)

Make the scrub repair commit, the scrub metadata commit and the
reconcile commit carry the trailer like every other rlsbl commit, or
record why they do not.

### 10. Rejected: healing path-keyed release records from move records

The `tree_hashes` premise is false (see the facts). A generic
move-record-driven path healer would need a Python reader of safegit's
record grammar that does not exist, would heal only `managed-files.json`
(already healed by regeneration) and `bases/` (better fixed at migration
time), and would make the commit graph a second authority for locations
the workspace declaration already answers — the same argument
`release_record.py` makes against `git describe`. A load-time
detect-and-heal has no trigger analogous to the journal seams and would
silently rewrite committed state.

## Open decisions

Each is self-contained; each blocks the item it names.

1. (Item 1) Where the recorded hash for a release ARCHIVE file lives,
   given that a file cannot carry its own hash.
2. (Item 2) When the commit tool is the git fallback (safegit absent from
   PATH), a declared move cannot be expressed: hard-error, making safegit
   a hard runtime dependency of `rename-releasable`, or warn once and
   commit unrecorded (which is the silent degradation the fleet forbids).
   Recommended: hard-error.
3. (Item 2, item 5) Whether `.validated` should be tracked at all. It is
   a cache holding a HEAD SHA, it defeats observed move inference on every
   directory move it rides, and it sits in a directory the layout calls
   handwritten. Untracking it changes the validation cache's semantics on
   fresh clones.
4. (Item 5, layout program) How `changelogs/` is split so the authorship
   axiom holds: released JSONL (immutable, handwritten) versus generated
   `.md` renderings versus `unreleased.jsonl` versus the cache. This is a
   layout decision the migrator cannot make.
5. (Item 5, layout program) Whether the layout guarantees one source per
   destination directory, or the migration becomes N move commits plus
   one rewrite commit.
6. (Item 5) Whether the migrator's rollback may restore rewritten files'
   bytes from HEAD's blobs (equivalent in effect to `git restore`, which
   agents are banned from running).
7. (Item 6) The mirror model for per-member state that leaves member
   territory.
8. (Item 8) For pre-record history: accept dangling hashes in historical
   trees, or add a range-scoped `--remap-shas-in`-style flag on rlsbl's
   side.
9. (Item 1, facts) Whether historical trees' release archives should be
   made self-consistent under a scrub at all (remap `candidate_sha` in
   history, which makes the archive's `tree_hashes` stale in the same
   tree the way the changelogs already are), or stay working-tree-only.
10. (Item 9) Trailer on the three commits, or a recorded reason.

## Dependencies and ordering

- Items 1, 2, 3, 9 are independent of the layout program and of each
  other; useful today. Item 2 also builds the `--moved` plumbing the
  migrator needs.
- Item 7 waits on a safegit release; the floor bump happens once, in the
  shared module item 2 creates.
- Item 4 ships in the layout-flip release and is dead code before it; it
  waits on decisions about the manifest and the key namespaces made in
  the layout program.
- Items 5, 6, 8 are inputs to the migrator's design and to the layout
  program's document; decisions 4, 5, 6, 7 must be made before the
  migrator is briefed.
